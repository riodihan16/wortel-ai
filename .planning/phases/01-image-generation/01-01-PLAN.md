<objective>
Add image generation to Wortel AI as a vertical MVP slice: the user picks an image-capable model on the active provider, types a prompt in the chat panel, the Go backend calls Kenari's `POST /v1/images/generations`, decodes whichever payload shape the provider returns (`b64_json` or `url`), persists the bytes locally, and renders the result inside the conversation — with a clear loading state, cancel, safe error messages, and PAYG billing honesty.

Purpose: This is the inverse of the attachments feature (ADR-054): bytes flow *from* the provider *to* local storage instead of user-to-provider. Reusing the attachments precedent (BLOB storage, `/attachments/{id}` asset route, `MessageItem` rendering, cascade delete) keeps the cross-cutting surface tiny and consistent.

Output: Working generation path end-to-end for the active provider, an ADR, an FR, and updated documentation.

**Architecture decision — where generated images live (justified, tradeoff noted):**
Generated images are stored as a **special assistant message** in the existing `messages` table (two new nullable columns `image_mime`, `image_data` added in migration v6), NOT in a separate gallery table. Rationale:
- Reuses the whole attachments spine: the `/attachments/{id}` route already looks up bytes by id; it is extended to also serve `messages.image_data` keyed by the message id.
- The chat transcript (`MessageItem` + `ChatPanel` list) already renders images from `/attachments/{id}`, so the result displays with **no new panel, navigation, or list surface** (AGENTS.md: no new abstractions, no inactive UI).
- `buildContext` (internal/app/context.go) only ever attaches Parts to **user** rows; assistant rows are text-only. So a generated image on an assistant row is **never silently re-sent** to a chat model on later turns, avoiding double billing.
- Cascade delete comes for free: deleting a conversation removes its messages, hence its images.
**Tradeoff (state to the user):** generated images are conversation-scoped — there is no cross-conversation gallery, and deleting the conversation deletes the image. A standalone gallery is explicitly deferred (see Out of Scope).

**Billing honesty (docs §12.4, §10.5):** image generation is never covered by a chat plan; it is always paid from PAYG balance, with possible cost reservation. The prompt bar shows this, and failure handling assumes a reservation may have been taken (the request is single-shot, never auto-retried).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user→backend | Prompt text and model id cross from React into Go via Wails bindings — untrusted input, validated in Go (non-empty prompt, model must be in the provider's configured list). |
| backend→Kenari | The Go backend sends the prompt + bearer key to `https://kenari.id/v1/images/generations` over HTTPS. |
| Kenari→backend | Provider response (JSON, `b64_json` or `url`) and any remote image bytes are untrusted input that must be sanitized/limited before storage or display. |
| backend→WebView | Generated bytes are served only through the local `/attachments/{uuid}` route; the WebView is never given a provider URL or raw base64 over IPC. |
